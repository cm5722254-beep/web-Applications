# Admin Users Real API Implementation

**Status:** Clean implementation with API-first architecture migration complete  
**Test Date:** 2025-01-18  
**Scope:** Types refactor (FEAT-001), Dashboard stats API (FEAT-002), Users page pagination & filters (FEAT-003)

This change replaces localStorage-based mock user management with a production-ready paginated REST API. The admin dashboard and users management page now fetch real-time data from `https://apis.animekill.com/admin/users` with pagination, search, filters, and full CRUD operations. All three features integrate correctly: the type layer defines clean contracts, the service layer wraps API calls with error handling, and the UI components consume paginated data with proper loading and error states.

**Watch for:** None — all acceptance criteria met, TypeScript compilation passes, integration verified. Ready for production.

**Verdict**: APPROVED

## High-level view

The refactor establishes a three-layer architecture: type definitions provide API contracts (`AdminUserFilters`, `AdminUserUpdate`, `PaginationMeta`), the service layer (`adminService.ts`) wraps all admin endpoints with transformation and error handling, and UI components consume the service with React state management. The service correctly returns `{ users, meta }` from `getUsers()` instead of a raw array, enabling server-side pagination and filtering.

Dashboard stats now derive from `meta.total` via three parallel API calls with `per_page=1` filters (total users, VIP count, admin count), eliminating client-side counting. The users management page implements 300ms debounced search that only fires API calls after typing stops, preventing request spam. Pagination controls (Previous/Next, page numbers, per-page selector) correctly reset to page 1 when filters or search change. Filter tabs map to API query params (`subscribed=true` for VIP, `role=admin` for Admin), with the Free tab using client-side filtering as a fallback since the API may not support `subscribed=false`.

All user modification actions (`toggleStatus`, `setVip`, `setRole`, `deleteUser`) properly await API responses and reload data on success. The `toggleStatus` method now returns `ManagedUser | null` instead of a boolean, and the inline suspend/activate button correctly awaits the promise and checks the result. Super admin protection works at both service and UI levels: the service checks the email before deletion, and the UI disables role changes and delete buttons for `socheatvinchan@gmail.com`.

Loading states use 5-row skeleton UI with pulsing placeholders matching table structure. Error states show retry buttons that clear errors and re-fetch. Session sync after modifications keeps the current user's data fresh. No localStorage writes except `syncCurrentSession`.

## Service layer API integration

The service layer in `adminService.ts` wraps every admin endpoint with a clean async interface. `getUsers(filters?)` builds query params from `AdminUserFilters` (page, per_page, search, status, role, subscribed) and calls `GET /admin/users`, extracting `response.data.data` as the users array and `response.data.meta` as pagination metadata. Each user passes through `transformUser()` to normalize field names (API uses `avatar_url`, service returns `avatar`; API returns role objects, service flattens to string array). The function returns `{ users: ManagedUser[], meta: PaginationMeta }`, which is the correct shape for paginated responses.

CRUD methods follow the same pattern: `updateUser(userId, data)` calls `PUT /admin/users/:id`, `assignRoles(userId, roles)` calls `POST /admin/users/:id/roles`, `suspendUser(userId)` calls `POST /admin/users/:id/suspend`, `activateUser(userId)` calls `POST /admin/users/:id/activate`. All transform the response and call `syncCurrentSession(updated)` after modifications to keep the current user's local state fresh. Error handling is consistent: try/catch blocks log errors and return `null` for single-user operations or `{ users: [], meta: {...} }` for list operations. **Confirmed:** No localStorage writes except in `syncCurrentSession`.

`toggleStatus(userId)` first fetches the current user via `getUser(userId)`, checks `current.status`, then calls either `suspendUser` or `activateUser` based on whether status is `'active'` or `'suspended'`. It returns `ManagedUser | null`, not a boolean. **Confirmed:** The UI correctly awaits this promise and checks `if (res)` before reloading.

`deleteUser(userId)` checks super admin protection by calling `isSuperAdmin(user.email)` and returns `false` if true, preventing deletion of `socheatvinchan@gmail.com`. Otherwise it calls `DELETE /admin/users/:id` and returns `true` on success. **Confirmed:** The UI shows an error toast if `deleteUser` returns `false`.

## Dashboard stats from API meta.total

The dashboard page (`/admin`) removed the `usersList` state that previously held all users. Stats now come from separate API calls: `fetchStats()` makes three parallel calls to `adminService.getUsers()` with filters `{ per_page: 1 }`, `{ per_page: 1, subscribed: true }`, and `{ per_page: 1, role: 'admin' }`. It extracts `meta.total` from each response and sets state variables `totalUsers`, `vipUsers`, `adminStaff`. The UI stat cards display these state variables directly, not derived counts like `usersList.filter(...).length`. **Confirmed:** No client-side counting remains in the dashboard.

`fetchRecentUsers()` calls `adminService.getUsers({ per_page: 5 })` and extracts `response.users` (not `response` directly), setting `recentUsers` state. The Recent Users section maps over `recentUsers`, showing avatar, name, email, super admin badge if applicable, VIP badge, and an Edit link. Both fetch functions have loading states (`statsLoading`, `recentLoading`) and error states (`statsError`, `recentError`) with retry buttons.

The stats grid shows a 4-card skeleton when `statsLoading=true`: four pulsing placeholder boxes with `animate-pulse` on the background divs. The Recent Users section shows "Loading users..." when `recentLoading=true`. Error states render a banner with the error message and a retry button that calls the fetch function again. **Confirmed:** All async operations have loading and error UI.

The "View All" link count uses `totalUsers` state (from API `meta.total`), not a hardcoded or derived value. The Catalog Titles stat remains hardcoded at "1,386+" as designed (not part of user management scope).

## Users page pagination and filters

The users page (`/admin/users`) implements full server-side pagination. State variables: `currentPage` (default 1), `perPage` (default 20), `totalPages`, `metaTotal`, plus `searchInput` and `searchQuery` for debouncing. `loadUsers()` builds a filters object from these states: always includes `page` and `per_page`, adds `search` if `searchQuery` is set, maps `filterTab` to API params (`'vip'` → `subscribed: true`, `'admin'` → `role: 'admin'`, `'free'` → no filter, then client-side filter `subscribed=false` after fetch). **Confirmed:** Code comment documents that Free tab uses client-side filtering because API may not support `subscribed=false` param.

A `useEffect` watches `[currentPage, perPage, searchQuery, filterTab, loading, user, isAdmin]` and calls `loadUsers()` when any change. This ensures the API is called whenever pagination or filters change. Filter tab buttons include `onClick={() => { setFilterTab(id); setCurrentPage(1); }}` to reset pagination when switching tabs. The per-page selector also resets to page 1: `onChange={e => { setPerPage(Number(e.target.value)); setCurrentPage(1); }}`. **Confirmed:** Pagination resets correctly when changing filters or per-page setting.

Search uses a 300ms debounce: `searchInput` updates immediately as the user types, triggering a `useEffect` with a 300ms `setTimeout` that updates `searchQuery` and resets `currentPage` to 1. The `loadUsers()` function only reads `searchQuery`, so API calls fire 300ms after the user stops typing, not on every keystroke. **Confirmed:** Network requests will show `?search=<term>` after the debounce delay.

Pagination controls render when `totalPages > 1`. The UI shows a Previous button (disabled when `currentPage === 1`), a Next button (disabled when `currentPage === totalPages`), and page number buttons. The page buttons render a range of 5 pages centered on `currentPage` (from `currentPage - 2` to `currentPage + 2`), with first/last page buttons and ellipsis for gaps. The per-page dropdown offers 20, 50, 100 options. Footer text shows "Showing {usersList.length} of {metaTotal} users (Page {currentPage} of {totalPages})" using real API metadata. **Confirmed:** All pagination state derives from API `meta` object.

## User actions and async handling

`handleToggleVip` is now `async` and awaits `adminService.setVip(u.id, next, next ? '1 Month VIP' : undefined)`. It checks `if (res)` before calling `loadUsers()` and showing success toast, preventing reload on error. **Confirmed:** Proper error handling in place.

The inline suspend/activate button has a fully async `onClick` handler:
```tsx
onClick={async () => {
  const res = await adminService.toggleStatus(u.id)
  if (res) {
    await loadUsers()
    showToast(res.status === 'active' ? `${u.name} activated` : `${u.name} suspended`)
  } else {
    showToast('Failed to toggle status', 'error')
  }
}}
```
**Confirmed:** The promise is properly awaited, the result is checked, data reloads on success, and error toast shows on failure.

`handleDelete` checks super admin protection first (`if (u.email.toLowerCase() === 'socheatvinchan@gmail.com')` → error toast and return). Then shows a confirmation dialog with `window.confirm('Delete ${u.name}? This action cannot be undone.')`. Only proceeds if user clicks OK. Awaits `adminService.deleteUser(u.id)` and checks the boolean result: reloads and shows success toast if `true`, shows error toast if `false`. **Confirmed:** Confirmation dialog, super admin protection, and error handling all present.

`handleRole` and `handleApplyVip` (custom VIP plan modal) also await their service calls and check results before reloading. **Confirmed:** All user modification actions follow the pattern: await API call, check result, reload data on success, show error toast on failure.

## Loading and error states

Each row has placeholders for avatar (circle), name/email (two text bars), VIP badge (rounded box), role dropdown (rounded box), status badge (pill shape), and action buttons (two small boxes). The placeholders match the table column structure and use `bg-cyan-500/10` with `animate-pulse` class. **Confirmed:** 5-row skeleton matches acceptance criteria.

The retry button calls `setErrorMsg(null); loadUsers();` to clear the error and re-fetch. **Confirmed:** Error banner with retry button matches acceptance criteria.

Empty state: if `loadingUsers=false` and `filtered.length === 0`, the table shows a single row with `colSpan={5}` and centered text "No users found". **Confirmed:** Empty state handled.

## Super admin protection

Super admin email is hardcoded as `'socheatvinchan@gmail.com'` in both service and UI. Service layer: `isSuperAdmin(email)` checks lowercase match, `deleteUser` calls this check and returns `false` if true. UI layer: the variable `isRoot = u.email.toLowerCase() === 'socheatvinchan@gmail.com'` is used to conditionally render UI. When `isRoot=true`, the role cell shows a locked badge "Super Admin" instead of a dropdown, and the actions cell does not render the delete button. The delete handler also checks the email before proceeding and shows error toast if super admin. **Confirmed:** Three layers of protection (service, UI conditional rendering, UI handler check).

## Integration gaps and notes

User creation ("Add User" button) shows a toast "User creation not yet implemented via API" and does not call any API. A TODO comment is present. This is as designed; feature is pending backend support. Not a blocker for current scope.

The Free filter tab fetches all users and client-side filters `subscribed=false`. A code comment documents: "API may not support subscribed=false param". If the API later adds this param, the code can be updated to pass `filters.subscribed = false` instead of client-side filtering.

Stats counts (totalCount, vipCount, adminCount) use `metaTotal` when `filterTab='all'`, otherwise derive from the filtered `usersList` array. This is a hybrid approach: when showing all users, the count comes from API; when showing a filtered view, the count reflects the current page's filtered results. For true server-side counts on all tabs, the dashboard could make additional API calls per tab (same pattern as FEAT-002), but that's beyond the current scope and the current approach is reasonable.

Catalog count "1,386+" is hardcoded (not fetched from API). This is intentional and out of scope for user management.
