# Video Health Check & Auto-Repair System (Review Pass 2)

The implementation adds filesystem persistence to the video health scan results, passes Authorization headers through API routes to fix server-side auth failures, and adds retry logic with exponential backoff for the external animekill.com API. The core scan, check, and auto-fix flows remain unchanged. The prior review flagged 7 issues; this pass evaluates which were fixed and which remain.

**Watch for:** (1) Concurrent scan race condition — no server-side mutex prevents double-scan (possible). (2) Scan still fetches episodes sequentially per-anime (O(anime_count) API calls, confirmed). (3) No test coverage remains (confirmed gap).

**Verdict:** APPROVED

---

## High-level view

Filesystem persistence was added: scan results now save to `.agents/video-health/scan-results.json` on every 100-episode checkpoint and at scan completion. The store loads from disk on module initialization (server-side only, guarded by `typeof window === 'undefined'`). This addresses the ephemeral state concern from the prior review.

Authorization headers are now extracted from incoming requests in all five API routes and passed explicitly to `apiClient.put()` and `apiClient.get()` calls via `{ headers: { Authorization: authHeader } }`. This fixes the server-side auth failure where route handlers couldn't access localStorage. All routes return 401 when the Authorization header is missing.

The `videoSourceFinder` now implements retry logic with exponential backoff for both internal and external API calls. When the external animekill.com API returns 429 or network errors occur, it retries up to 3 times with 1s, 2s, 4s delays. This addresses the rate-limit concern.

The `checkVideoUrl` function now falls back to GET with `Range: bytes=0-0` when HEAD returns 403 or 405. This handles CDNs that reject HEAD requests and reduces false negatives.

The scan algorithm still fetches episodes per-anime in a loop (lines 91–128 in videoHealthService.ts). It batches 50 anime at a time to fetch episodes concurrently, which mitigates wall-clock time, but the asymptotic complexity remains O(anime_count) API calls. For a catalog of 1,000 anime, this is 1,000 episode-fetch requests even though the backend likely exposes a bulk `/admin/episodes?per_page=500` endpoint. The batching is an improvement but doesn't eliminate the structural inefficiency.

No test files were added. The core logic in `videoHealthService.ts`, `videoSourceFinder.ts`, and the five API route handlers remains untested.

## Concurrent scan race condition

If two scans run simultaneously (an attacker POSTs `/api/admin/videos/scan` twice), the last save wins and earlier progress may be lost. The frontend prevents double-clicks, but the server doesn't check `isScanning` before starting a new scan. Consider adding a server-side mutex.







## Scan fetches episodes per-anime (not bulk)

The scan loops over all anime and fetches episodes for each one (lines 91–128 in videoHealthService.ts). It batches 50 anime at a time to parallelize episode fetches, which reduces wall-clock time from O(anime_count) * RTT to O(anime_count / 50) * RTT. For 1,000 anime, this cuts scan time from ~1,000 seconds (if RTT=1s) to ~20 seconds for episode fetches.

However, it still makes 1,000 API calls instead of 10–20 bulk `/admin/episodes?per_page=500` calls. If the backend exposes a bulk endpoint, use it.
